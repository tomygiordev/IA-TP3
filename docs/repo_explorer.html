01 / flujo del sistema

La arquitectura queda como una linea de montaje auditable.

Click en cada bloque para ver por que existe. La clave es que test no se usa para elegir hiperparametros y que el vectorizador solo aprende del conjunto de entrenamiento.

Hugging Face dataset

Se usa `cornell-movie-review-data/rotten_tomatoes` porque es binario, manejable y trae splits definidos.

  • Evita perder tiempo buscando un dataset gigante.
  • Permite entrenar muchas veces en una PC comun.
  • Encaja directo con salida sigmoide y binary crossentropy.

03 / hiperparametros

Los experimentos no son decoracion: prueban capacidad, ritmo y regularizacion.

La seleccion se hace por F1 de validacion. Test queda reservado para reportar desempeno final.

e3_regularized

Regularizacion con Dropout 0.5 y L2 0.0001. Gana por F1 de validacion.

Los graficos muestran comportamiento, no solo numeros sueltos.

La curva de overfitting es especialmente util: train queda perfecto mientras validacion se degrada.

05 / modo critico

Preguntas incomodas, respuestas preparadas.

Este bloque esta pensado para el companero que revisa todo. Si una decision no se puede defender, no deberia estar en el repo.

La respuesta corta: hicimos menos cosas, pero las hicimos trazables.

El TP no necesita una arquitectura de moda. Necesita demostrar que se entiende entrenamiento, validacion, sobreajuste, hiperparametros y metricas.

  • Consigna cubierta: Keras Sequential, MLP, Hugging Face y clasificacion binaria.
  • Buenas practicas: sin adaptar vectorizador con test, sin elegir modelo por test.
  • Evidencia: metricas, matriz de confusion y curvas separadas.
Porque la consigna pide MLP y Keras Sequential. Usar Transformers resolveria otro problema y haria mas dificil defender el objetivo teorico del TP.
